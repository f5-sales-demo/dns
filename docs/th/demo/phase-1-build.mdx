เฟส 1 ปรับใช้ **primary DNS zone** แบบ authoritative บน F5 Distributed Cloud ด้วย Terraform โดยมี
remote state สำรองอยู่ใน Azure Blob Storage หน้านี้แสดงทุกไฟล์ใน plan อธิบายตัวแปรและ secrets ที่จำเป็น
และครอบคลุมทั้งการรันแบบ local และ GitHub Actions pipeline

## สิ่งที่คุณปรับใช้

- `xcsh_dns_zone` สำหรับโดเมนที่มอบหมายให้คุณ ใน namespace `system` พร้อมกลุ่ม `demo-records`
  ของ A records (`www`, `app`, `api`)
- Terraform state ที่จัดเก็บใน Azure Blob Storage container เพื่อให้ state เดียวกันถูกใช้ร่วมกัน
  ระหว่างเครื่องของคุณและ CI

<Aside type="note">
ออบเจกต์ DNS ต้องสร้างใน namespace `system` — F5 XC API จะปฏิเสธ namespace อื่น
ชื่อ zone ต้องเป็นโดเมนที่บัญชีของคุณเป็นเจ้าของ และ TTL ของ record ต้องมีอย่างน้อย 60 วินาที
</Aside>

## Plan

Plan อยู่ภายใต้ `terraform/`: root module บาง ๆ ที่เชื่อมต่อ input เข้ากับ module `dns-zone`

### versions.tf

กำหนดเวอร์ชัน Terraform และ provider การจำกัด provider คือ `>= 3.61.15` — release แรกใน registry
ที่มี DNS resources

```hcl
terraform {
  required_version = ">= 1.5"

  required_providers {
    xcsh = {
      source = "f5-sales-demo/xcsh"
      # >= 3.61.16: the namespace attribute for system-only DNS resources defaults
      # to "system" (spec-driven), so it can be omitted. Locally the provider is
      # consumed via dev_overrides, which ignores this constraint.
      version = ">= 3.61.16"
    }
  }
}
```

### providers.tf

Provider ไม่รับอาร์กิวเมนต์ในโค้ด — มันยืนยันตัวตนจาก environment ดังนั้นจึงไม่มี secrets ถูก commit

```hcl
# The xcsh provider authenticates from the environment — no secrets in code.
# Export one of the following credential sets before running Terraform:
#
#   Token auth:  XCSH_API_URL + XCSH_API_TOKEN
#   P12 auth:    XCSH_API_URL + XCSH_P12_FILE + XCSH_P12_PASSWORD
#   PEM auth:    XCSH_API_URL + XCSH_CERT + XCSH_KEY
#
# See terraform/README.md for local dev setup (dev_overrides + env).
provider "xcsh" {}
```

### backend.tf

Backend `azurerm` แบบ **partial**: ไม่มีค่าเฉพาะ environment ถูก hardcode ไว้ ค่าพิกัดจะถูกส่งมา
ในช่วง `init` (จากไฟล์ local หรือจาก GitHub Actions variables ใน CI)

```hcl
terraform {
  # Azure Blob Storage remote state, configured as a PARTIAL backend:
  # no environment-specific values are hardcoded here. Supply them at init time.
  #
  #   CI:    terraform init -backend-config="resource_group_name=$RG" ...
  #          (values from GitHub Actions repository variables)
  #   Local: terraform init -backend-config=backend.hcl   (copy backend.hcl.example; gitignored)
  #
  # Auth is the storage account access key via the ARM_ACCESS_KEY environment
  # variable (never committed). Keyless auth (use_oidc / use_azuread_auth) is not
  # used: our Contributor-only RBAC cannot assign the "Storage Blob Data
  # Contributor" role those methods require.
  backend "azurerm" {}
}
```

### variables.tf

`domain` เป็น required (ส่งมาในช่วง runtime ไม่ถูก hardcode); `a_records` แมปชื่อ record แต่ละรายการ
ไปยัง IPv4 addresses ไม่มีตัวแปร `namespace` — provider กำหนด DNS objects ไว้ใน namespace `system`
จาก constraint ของ API spec ดังนั้นจึงไม่ถูกกำหนดค่าที่นี่

```hcl
variable "domain" {
  description = "DNS zone FQDN (required; supplied via TF_VAR_domain / a GitHub variable / tfvars)."
  type        = string
}

variable "labels" {
  description = "Labels applied to managed DNS objects."
  type        = map(string)
  default = {
    managed_by = "terraform"
    use_case   = "dns"
  }
}

variable "a_records" {
  description = "A records: record name (\"\" = apex) to list of IPv4 addresses."
  type        = map(list(string))
  default = {
    www = ["203.0.113.10"]
    app = ["203.0.113.20"]
    api = ["203.0.113.30"]
  }
}
```

<Aside type="tip">
A records ค่าเริ่มต้นใช้ที่อยู่เอกสาร RFC 5737 (`203.0.113.0/24`) ซึ่งไม่สามารถ route ได้
แทนที่ด้วย targets จริงสำหรับการสาธิตแบบ live
</Aside>

### main.tf และ dns-zone module

Root module เชื่อมต่อ input เข้ากับ `./modules/dns-zone`:

```hcl
module "dns_zone" {
  source = "./modules/dns-zone"

  domain    = var.domain
  labels    = var.labels
  a_records = var.a_records
}
```

Module สร้าง zone (namespace ถูกละเว้น — provider กำหนดค่าเริ่มต้นเป็น `system`) บล็อก
`dynamic "rr_set"` แปลง map `a_records` เป็น record set หนึ่งรายการต่อรายการ:

```hcl
resource "xcsh_dns_zone" "this" {
  name   = var.domain
  labels = var.labels

  primary {
    default_soa_parameters {}

    rr_set_group {
      metadata {
        name = "demo-records"
      }

      dynamic "rr_set" {
        for_each = var.a_records
        content {
          ttl = var.record_ttl
          a_record {
            name   = rr_set.key
            values = rr_set.value
          }
        }
      }
    }
  }
}
```

Root `outputs.tf` ส่งออกชื่อ zone และ F5 XC identifier จาก module อีกครั้ง

## ตัวแปรและ secrets ที่จำเป็น

ไม่มีอะไรเฉพาะ environment ถูกฝังไว้ในไฟล์ `.tf` ทุกอย่างถูกส่งมาในช่วง runtime — จาก GitHub Actions
**variables** และ **secrets** ใน CI หรือจากไฟล์ local และ environment variables

| ค่า | วัตถุประสงค์ | แหล่งที่มาใน CI | แหล่งที่มาใน Local |
| --- | --- | --- | --- |
| `resource_group_name`, `storage_account_name`, `container_name`, `key` | พิกัด azurerm backend | Repository **variables** `TFSTATE_RESOURCE_GROUP`, `TFSTATE_STORAGE_ACCOUNT`, `TFSTATE_CONTAINER`, `TFSTATE_KEY` (ส่งผ่าน `-backend-config`) | `backend.hcl` (copy `backend.hcl.example`; gitignored) |
| `domain` | Terraform input | Repository **variable** `DNS_DOMAIN` (เป็น `TF_VAR_domain`) | `terraform.tfvars` (copy ตัวอย่าง) หรือ `TF_VAR_domain` |
| `ARM_ACCESS_KEY` | azurerm backend auth (storage account key) | Repository **secret** | `export ARM_ACCESS_KEY=...` |
| `XCSH_API_URL`, `XCSH_API_TOKEN` | xcsh provider auth | Repository **secrets** | `export XCSH_API_URL=... XCSH_API_TOKEN=...` |

ไฟล์ตัวอย่างสองไฟล์ที่มาพร้อมกับ repo:

<Tabs>
<TabItem label="backend.hcl.example">

```hcl
resource_group_name  = "f5-sales-demo-tfstate"
storage_account_name = "f5salesdemotfstate"
container_name       = "tfstate"
key                  = "dns.tfstate"
```

</TabItem>
<TabItem label="terraform.tfvars.example">

```hcl
domain = "f5-sales-demo.com"

labels = {
  managed_by = "terraform"
  use_case   = "dns"
}

a_records = {
  www = ["203.0.113.10"]
  app = ["203.0.113.20"]
  api = ["203.0.113.30"]
}
```

</TabItem>
</Tabs>

<Aside type="caution">
Backend auth ใช้ storage account access key (`ARM_ACCESS_KEY`) แทนที่จะเป็น keyless OIDC / Azure AD
การเข้าถึง data-plane แบบ keyless ต้องการ role *Storage Blob Data Contributor* ซึ่ง subscription
แบบ Contributor-only ไม่สามารถกำหนดได้ access key อยู่เฉพาะใน environment หรือ GitHub secret เท่านั้น
— มันไม่ถูก commit ไว้
</Aside>

## Bootstrap Azure state backend

Backend storage ไม่สามารถจัดเก็บ bootstrap ของตัวเองได้ ดังนั้นให้สร้างครั้งเดียว นอกกระบวนการปกติ
ด้วย Azure CLI session ที่ยืนยันตัวตนแล้ว repo มีสคริปต์ `scripts/bootstrap-azure-state.sh`:

```sh
az group create --name f5-sales-demo-tfstate --location eastus2 \
  --tags managed_by=terraform use_case=dns purpose=tfstate

az storage account create --name f5salesdemotfstate --resource-group f5-sales-demo-tfstate \
  --location eastus2 --sku Standard_LRS --kind StorageV2 \
  --min-tls-version TLS1_2 --allow-blob-public-access false

# State safety: keep prior versions and allow recovery of deleted state blobs.
az storage account blob-service-properties update \
  --account-name f5salesdemotfstate --resource-group f5-sales-demo-tfstate \
  --enable-versioning true \
  --enable-delete-retention true --delete-retention-days 7 \
  --enable-container-delete-retention true --container-delete-retention-days 7

KEY="$(az storage account keys list \
  --account-name f5salesdemotfstate --resource-group f5-sales-demo-tfstate \
  --query '[0].value' -o tsv)"

az storage container create --name tfstate \
  --account-name f5salesdemotfstate --auth-mode key --account-key "$KEY"
```

จากนั้น export key สำหรับการรัน local และตั้งค่า (พร้อม provider credentials) เป็น GitHub secrets:

```sh
export ARM_ACCESS_KEY="$KEY"
gh secret set ARM_ACCESS_KEY -R f5-sales-demo/dns
gh secret set XCSH_API_URL   -R f5-sales-demo/dns
gh secret set XCSH_API_TOKEN -R f5-sales-demo/dns
```

## ปรับใช้แบบ local

<Steps>

1. **กำหนดค่า inputs.** Copy ตัวอย่างและกรอกค่าของคุณ:

   ```sh
   cp terraform/backend.hcl.example terraform/backend.hcl
   cp terraform/terraform.tfvars.example terraform/terraform.tfvars
   ```

2. **Export credentials:**

   ```sh
   export XCSH_API_URL="https://<tenant>.console.ves.volterra.io"
   export XCSH_API_TOKEN="<api-token>"
   export ARM_ACCESS_KEY="<storage-account-key>"
   ```

3. **Initialize** backend ด้วย partial config:

   ```sh
   cd terraform
   terraform init -backend-config=backend.hcl
   ```

4. **ตรวจสอบ formatting และ validate:**

   ```sh
   terraform fmt -check -recursive
   terraform validate
   ```

5. **Plan และ apply:**

   ```sh
   terraform plan
   terraform apply
   ```

</Steps>

การ apply ที่สำเร็จจะสร้าง zone และเขียน state ไปยัง Azure container ต่อไปที่
[เฟส 2 — ตรวจสอบ](/dns/demo/phase-2-validate/) เพื่อยืนยันว่ามันแก้ไข DNS ได้

## Continuous integration

Workflow `.github/workflows/terraform.yml` รัน **plan** ในทุก pull request และ **apply**
เมื่อ merge ไปยัง `main` มันอ่านพิกัด backend และ inputs จาก repository variables และ
credentials จาก secrets โดย inject แต่ละรายการเฉพาะในขั้นตอนที่ต้องการ และกำหนดลำดับการรัน
บน concurrency group เพื่อไม่ให้ apply สองรายการแข่งกันบน state blob ที่ใช้ร่วมกัน

```yaml
name: Terraform

on:
  pull_request:
    branches: [main]
    paths: ['terraform/**', '.github/workflows/terraform.yml']
  push:
    branches: [main]
    paths: ['terraform/**']

permissions:
  contents: read

concurrency:
  group: terraform-state
  cancel-in-progress: false

env:
  TF_IN_AUTOMATION: 'true'

jobs:
  terraform:
    name: ${{ github.event_name == 'push' && 'apply' || 'plan' }}
    runs-on: ubuntu-latest
    defaults:
      run:
        working-directory: terraform
    steps:
      - name: Checkout
        uses: actions/checkout@9c091bb21b7c1c1d1991bb908d89e4e9dddfe3e0 # v7.0.0

      - name: Setup Terraform
        uses: hashicorp/setup-terraform@dfe3c3f87815947d99a8997f908cb6525fc44e9e # v4.0.1

      - name: Init
        env:
          ARM_ACCESS_KEY: ${{ secrets.ARM_ACCESS_KEY }}
          RESOURCE_GROUP: ${{ vars.TFSTATE_RESOURCE_GROUP }}
          STORAGE_ACCOUNT: ${{ vars.TFSTATE_STORAGE_ACCOUNT }}
          CONTAINER: ${{ vars.TFSTATE_CONTAINER }}
          STATE_KEY: ${{ vars.TFSTATE_KEY }}
        run: |
          terraform init -input=false \
            -backend-config="resource_group_name=${RESOURCE_GROUP}" \
            -backend-config="storage_account_name=${STORAGE_ACCOUNT}" \
            -backend-config="container_name=${CONTAINER}" \
            -backend-config="key=${STATE_KEY}"

      - name: Format check
        run: terraform fmt -check -recursive

      - name: Validate
        run: terraform validate -no-color

      - name: Plan
        if: github.event_name == 'pull_request'
        env:
          ARM_ACCESS_KEY: ${{ secrets.ARM_ACCESS_KEY }}
          XCSH_API_URL: ${{ secrets.XCSH_API_URL }}
          XCSH_API_TOKEN: ${{ secrets.XCSH_API_TOKEN }}
          TF_VAR_domain: ${{ vars.DNS_DOMAIN }}
        run: terraform plan -input=false -no-color

      - name: Apply
        if: github.event_name == 'push'
        env:
          ARM_ACCESS_KEY: ${{ secrets.ARM_ACCESS_KEY }}
          XCSH_API_URL: ${{ secrets.XCSH_API_URL }}
          XCSH_API_TOKEN: ${{ secrets.XCSH_API_TOKEN }}
          TF_VAR_domain: ${{ vars.DNS_DOMAIN }}
        run: terraform apply -input=false -auto-approve -no-color
```

actions ถูก pin ไว้ที่ commit SHAs (พร้อม version comments) และ secrets ถูก scope ไว้ที่ขั้นตอน
`init`, `plan`, และ `apply` แทนที่จะเป็นทั้ง job
