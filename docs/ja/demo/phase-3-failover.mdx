フェーズ 3 は、[フェーズ 1](/dns/demo/phase-1-build/) のゾーンの上に**ヘルスチェック付きフェイルオーバー**を追加します。F5 XC の **DNS ロードバランサー**は、プールのヘルス状態に基づいて名前に対して異なる応答を返すため、トラフィックは自動的に正常なプールに移動します。

<Aside type="caution" title="dns-lb モジュール待ち">
このフェーズはまだ実行可能ではありません。`lb_record` のワイヤーフォーマットの固定待ちによりブロックされている現在の計画のフォローアップである `dns-lb` Terraform モジュールに依存しています。このページは意図した設計を文書化しており、全体のアークが完結するようにしています。実行可能な手順はモジュールとともに提供されます。
</Aside>

## 予定設計

DNS ロードバランサースタックは、3 つの F5 XC リソースとゾーン内の 1 つのレコードで構成されます。

| リソース | 役割 |
| --- | --- |
| `xcsh_dns_lb_health_check` | 各メンバーをプローブし（HTTP、HTTPS、TCP、ICMP、または UDP）、プールのヘルス状態を判定します |
| `xcsh_dns_lb_pool` | ロードバランシングモード（`ROUND_ROBIN`、`PRIORITY` など）とヘルスチェックへの参照を持つメンバーのセット |
| `xcsh_dns_load_balancer` | リクエストごとにプールを選択するルール（フォールバックプール付き） |
| `lb_record`（`xcsh_dns_zone` 内） | ゾーン内の名前を DNS ロードバランサーにバインドします |

`dns-lb` モジュールはこれらを表現し、ゾーンモジュールはロードバランサーを指す `lb_record` エントリを持つように拡張されます — これにより、単一の `terraform apply` でフェイルオーバーパス全体が構築されます。

## 予定デモ

モジュールがリリースされると、フェイルオーバーデモでは以下を実施します。

1. ヘルスチェックを使用して、DNS ロードバランサーの背後に 2 つのプール（プライマリとセカンダリ）をデプロイします。
2. ロードバランシングされた名前を解決し、プライマリプールの応答が返されることを確認します。
3. プライマリを非正常な状態にし、解決がセカンダリにフェイルオーバーすることを確認します — レディネスゲートは応答が変わるまで `dig` をポーリングします。
4. プライマリを復元し、フェイルバックを確認します。

それまでは、[フェーズ 4 — ティアダウン](/dns/demo/phase-4-teardown/)に進んで、フェーズ 1 のゾーンを削除してください。
