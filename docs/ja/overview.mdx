このユースケースは、Terraform を使用して **F5 Distributed Cloud 上の権威 DNS** を管理します。小規模で再利用可能なプランは、委任されたドメインのプライマリ DNS ゾーンとそのレコードを作成し、状態を **Azure Blob Storage** に保存し、**GitHub Actions** を通じてプルリクエスト時のプラン実行とマージ時のアプライを行います。

## 管理対象

- `xcsh_dns_zone` — F5 XC `system` 名前空間内の権威**プライマリ**ゾーン（A レコード付き）。ゾーン名は委任されたドメイン（変数）であるため、対象の変更は設定変更であり、コード変更ではありません。
- Azure 上のリモート Terraform 状態。これにより、オペレーターのマシンと CI 間での実行共有が可能になります。

## アーキテクチャ

| レイヤー | 選択 | 理由 |
| --- | --- | --- |
| プロバイダー | `f5-sales-demo/xcsh`（Terraform レジストリ） | F5 XC OpenAPI から生成され、`xcsh_dns_zone` および DNS ロードバランサーリソースを管理します。API トークン（`Authorization: APIToken <token>`）で認証します。 |
| 状態バックエンド | `azurerm`（Azure Blob Storage）、アクセスキー認証 | 耐久性のある共有状態。サブスクリプションが Contributor のみを付与しており、キーなし（OIDC / Azure AD）認証に必要な *Storage Blob Data Contributor* ロールを割り当てられないため、アクセスキー認証を使用しています。 |
| 自動化 | GitHub Actions | すべてのプルリクエストでプランを実行し、`main` へのマージ時にアプライを実行します。バックエンドの設定と入力はリポジトリの**変数**から取得し、認証情報は**シークレット**から取得します。 |

<Aside type="note">
すべての F5 XC DNS オブジェクトは `system` 名前空間に配置する必要があります — API は他の名前空間を拒否します。プランでは変数バリデーションルールによってこれを強制しています。
</Aside>

## 始め方

[デモ](/dns/demo/)セクションでは、ライフサイクル全体をエンドツーエンドで説明しています：Terraform でゾーンを**構築**し、解決されることを**検証**し、DNS ロードバランサーで**フェイルオーバー**を行い、**ティアダウン**します。まず [フェーズ 1 — 構築](/dns/demo/phase-1-build/) から始めてください。これには、ゾーンのデプロイに関する完全なハウツーガイドが含まれており、すべての Terraform ファイル、CI ワークフロー、および必要な変数とシークレットが記載されています。
