चरण 1 Terraform के साथ F5 Distributed Cloud पर एक आधिकारिक **प्राथमिक DNS ज़ोन** तैनात करता है, जो
Azure Blob Storage में रिमोट स्टेट द्वारा समर्थित है। यह पृष्ठ प्लान की प्रत्येक फ़ाइल दिखाता है, आवश्यक
चर और रहस्यों की व्याख्या करता है, और स्थानीय रन तथा GitHub Actions पाइपलाइन दोनों को कवर करता है।

## आप क्या तैनात करते हैं

- आपके डेलिगेटेड डोमेन के लिए `xcsh_dns_zone`, `system` नेमस्पेस में, A रिकॉर्ड (`www`, `app`, `api`) के एक `demo-records` समूह के साथ।
- Azure Blob Storage कंटेनर में संग्रहीत Terraform स्टेट, ताकि आपकी मशीन और CI के बीच एक ही स्टेट साझा हो।

<Aside type="note">
DNS ऑब्जेक्ट `system` नेमस्पेस में बनाए जाने चाहिए — F5 XC कंसोल API अन्य नेमस्पेस को अस्वीकार करता है।
ज़ोन का नाम वह डोमेन होना चाहिए जिसका आपका खाता स्वामी है, और रिकॉर्ड TTL कम से कम 60 सेकंड होनी चाहिए।
</Aside>

## प्लान

प्लान `terraform/` के अंतर्गत रहता है: एक पतला रूट मॉड्यूल जो इनपुट को `dns-zone` मॉड्यूल में जोड़ता है।

### versions.tf

Terraform और प्रोवाइडर को पिन करता है। प्रोवाइडर बाधा `>= 3.61.15` है — पहला रजिस्ट्री रिलीज़
जो DNS संसाधन भेजता है।

```hcl
terraform {
  required_version = ">= 1.5"

  required_providers {
    xcsh = {
      source = "f5-sales-demo/xcsh"
      # >= 3.61.16: the namespace attribute for system-only DNS resources defaults
      # to "system" (spec-driven), so it can be omitted. Locally the provider is
      # consumed via dev_overrides, which ignores this constraint.
      version = ">= 3.61.16"
    }
  }
}
```

### providers.tf

प्रोवाइडर कोड में कोई तर्क नहीं लेता — यह पर्यावरण से प्रमाणीकरण करता है, इसलिए कोई रहस्य
कमिट नहीं किया जाता।

```hcl
# The xcsh provider authenticates from the environment — no secrets in code.
# Export one of the following credential sets before running Terraform:
#
#   Token auth:  XCSH_API_URL + XCSH_API_TOKEN
#   P12 auth:    XCSH_API_URL + XCSH_P12_FILE + XCSH_P12_PASSWORD
#   PEM auth:    XCSH_API_URL + XCSH_CERT + XCSH_KEY
#
# See terraform/README.md for local dev setup (dev_overrides + env).
provider "xcsh" {}
```

### backend.tf

एक **आंशिक** `azurerm` बैकएंड: कोई पर्यावरण-विशिष्ट मान हार्डकोड नहीं किया गया। निर्देशांक
`init` समय पर आपूर्ति किए जाते हैं (एक स्थानीय फ़ाइल से, या CI में GitHub Actions चर से)।

```hcl
terraform {
  # Azure Blob Storage remote state, configured as a PARTIAL backend:
  # no environment-specific values are hardcoded here. Supply them at init time.
  #
  #   CI:    terraform init -backend-config="resource_group_name=$RG" ...
  #          (values from GitHub Actions repository variables)
  #   Local: terraform init -backend-config=backend.hcl   (copy backend.hcl.example; gitignored)
  #
  # Auth is the storage account access key via the ARM_ACCESS_KEY environment
  # variable (never committed). Keyless auth (use_oidc / use_azuread_auth) is not
  # used: our Contributor-only RBAC cannot assign the "Storage Blob Data
  # Contributor" role those methods require.
  backend "azurerm" {}
}
```

### variables.tf

`domain` आवश्यक है (रनटाइम पर आपूर्ति किया जाता है, कभी हार्डकोड नहीं); `a_records` प्रत्येक रिकॉर्ड नाम को
उसके IPv4 पतों से मैप करता है। कोई `namespace` चर नहीं है — प्रोवाइडर API स्पेक की बाधा से DNS
ऑब्जेक्ट को `system` नेमस्पेस में स्थिर करता है, इसलिए इसे यहाँ कभी कॉन्फ़िगर नहीं किया जाता।

```hcl
variable "domain" {
  description = "DNS zone FQDN (required; supplied via TF_VAR_domain / a GitHub variable / tfvars)."
  type        = string
}

variable "labels" {
  description = "Labels applied to managed DNS objects."
  type        = map(string)
  default = {
    managed_by = "terraform"
    use_case   = "dns"
  }
}

variable "a_records" {
  description = "A records: record name (\"\" = apex) to list of IPv4 addresses."
  type        = map(list(string))
  default = {
    www = ["203.0.113.10"]
    app = ["203.0.113.20"]
    api = ["203.0.113.30"]
  }
}
```

<Aside type="tip">
डिफ़ॉल्ट A रिकॉर्ड RFC 5737 दस्तावेज़ीकरण पते (`203.0.113.0/24`) उपयोग करते हैं, जो रूटेबल नहीं हैं।
लाइव डेमो के लिए उन्हें वास्तविक लक्ष्यों से बदलें।
</Aside>

### main.tf और dns-zone मॉड्यूल

रूट मॉड्यूल इनपुट को `./modules/dns-zone` में जोड़ता है:

```hcl
module "dns_zone" {
  source = "./modules/dns-zone"

  domain    = var.domain
  labels    = var.labels
  a_records = var.a_records
}
```

मॉड्यूल ज़ोन बनाता है (नेमस्पेस छोड़ा गया है — प्रोवाइडर इसे `system` पर डिफ़ॉल्ट करता है)। एक
`dynamic "rr_set"` ब्लॉक `a_records` मैप को प्रति प्रविष्टि एक रिकॉर्ड सेट में बदलता है:

```hcl
resource "xcsh_dns_zone" "this" {
  name   = var.domain
  labels = var.labels

  primary {
    default_soa_parameters {}

    rr_set_group {
      metadata {
        name = "demo-records"
      }

      dynamic "rr_set" {
        for_each = var.a_records
        content {
          ttl = var.record_ttl
          a_record {
            name   = rr_set.key
            values = rr_set.value
          }
        }
      }
    }
  }
}
```

रूट `outputs.tf` मॉड्यूल से ज़ोन नाम और F5 XC पहचानकर्ता को पुनः निर्यात करता है।

## आवश्यक चर और रहस्य

`.tf` फ़ाइलों में कोई पर्यावरण-विशिष्ट जानकारी नहीं बेक की गई है। सब कुछ रनटाइम पर आपूर्ति
किया जाता है — CI में GitHub Actions **चर** और **रहस्य** से, या स्थानीय फ़ाइलों और पर्यावरण चरों से।

| मान | उद्देश्य | CI स्रोत | स्थानीय स्रोत |
| --- | --- | --- | --- |
| `resource_group_name`, `storage_account_name`, `container_name`, `key` | azurerm बैकएंड निर्देशांक | रिपॉज़िटरी **चर** `TFSTATE_RESOURCE_GROUP`, `TFSTATE_STORAGE_ACCOUNT`, `TFSTATE_CONTAINER`, `TFSTATE_KEY` (`-backend-config` के माध्यम से पारित) | `backend.hcl` (`backend.hcl.example` की प्रतिलिपि बनाएं; gitignored) |
| `domain` | Terraform इनपुट | रिपॉज़िटरी **चर** `DNS_DOMAIN` (`TF_VAR_domain` के रूप में) | `terraform.tfvars` (उदाहरण की प्रतिलिपि) या `TF_VAR_domain` |
| `ARM_ACCESS_KEY` | azurerm बैकएंड ऑथ (स्टोरेज अकाउंट की) | रिपॉज़िटरी **रहस्य** | `export ARM_ACCESS_KEY=...` |
| `XCSH_API_URL`, `XCSH_API_TOKEN` | xcsh प्रोवाइडर ऑथ | रिपॉज़िटरी **रहस्य** | `export XCSH_API_URL=... XCSH_API_TOKEN=...` |

रेपो में शामिल दो उदाहरण फ़ाइलें:

<Tabs>
<TabItem label="backend.hcl.example">

```hcl
resource_group_name  = "f5-sales-demo-tfstate"
storage_account_name = "f5salesdemotfstate"
container_name       = "tfstate"
key                  = "dns.tfstate"
```

</TabItem>
<TabItem label="terraform.tfvars.example">

```hcl
domain = "f5-sales-demo.com"

labels = {
  managed_by = "terraform"
  use_case   = "dns"
}

a_records = {
  www = ["203.0.113.10"]
  app = ["203.0.113.20"]
  api = ["203.0.113.30"]
}
```

</TabItem>
</Tabs>

<Aside type="caution">
बैकएंड ऑथ स्टोरेज अकाउंट एक्सेस की (`ARM_ACCESS_KEY`) का उपयोग करता है, न कि कीलेस OIDC / Azure
AD का। कीलेस डेटा-प्लेन एक्सेस के लिए *Storage Blob Data Contributor* भूमिका की आवश्यकता है, जिसे
Contributor-only सब्सक्रिप्शन असाइन नहीं कर सकता। एक्सेस की केवल पर्यावरण या GitHub रहस्य में
रहती है — इसे कभी कमिट नहीं किया जाता।
</Aside>

## Azure स्टेट बैकएंड को बूटस्ट्रैप करें

बैकएंड स्टोरेज अपना स्वयं का बूटस्ट्रैप संग्रहीत नहीं कर सकता, इसलिए इसे एक बार, बाहर से,
प्रमाणित Azure CLI सत्र के साथ बनाएं। रेपो `scripts/bootstrap-azure-state.sh` भेजता है:

```sh
az group create --name f5-sales-demo-tfstate --location eastus2 \
  --tags managed_by=terraform use_case=dns purpose=tfstate

az storage account create --name f5salesdemotfstate --resource-group f5-sales-demo-tfstate \
  --location eastus2 --sku Standard_LRS --kind StorageV2 \
  --min-tls-version TLS1_2 --allow-blob-public-access false

# State safety: keep prior versions and allow recovery of deleted state blobs.
az storage account blob-service-properties update \
  --account-name f5salesdemotfstate --resource-group f5-sales-demo-tfstate \
  --enable-versioning true \
  --enable-delete-retention true --delete-retention-days 7 \
  --enable-container-delete-retention true --container-delete-retention-days 7

KEY="$(az storage account keys list \
  --account-name f5salesdemotfstate --resource-group f5-sales-demo-tfstate \
  --query '[0].value' -o tsv)"

az storage container create --name tfstate \
  --account-name f5salesdemotfstate --auth-mode key --account-key "$KEY"
```

फिर स्थानीय रन के लिए की को एक्सपोर्ट करें, और इसे (प्रोवाइडर क्रेडेंशियल के साथ) GitHub रहस्य के रूप में सेट करें:

```sh
export ARM_ACCESS_KEY="$KEY"
gh secret set ARM_ACCESS_KEY -R f5-sales-demo/dns
gh secret set XCSH_API_URL   -R f5-sales-demo/dns
gh secret set XCSH_API_TOKEN -R f5-sales-demo/dns
```

## स्थानीय रूप से तैनात करें

<Steps>

1. **इनपुट कॉन्फ़िगर करें।** उदाहरणों की प्रतिलिपि बनाएं और अपने मान भरें:

   ```sh
   cp terraform/backend.hcl.example terraform/backend.hcl
   cp terraform/terraform.tfvars.example terraform/terraform.tfvars
   ```

2. **क्रेडेंशियल एक्सपोर्ट करें:**

   ```sh
   export XCSH_API_URL="https://<tenant>.console.ves.volterra.io"
   export XCSH_API_TOKEN="<api-token>"
   export ARM_ACCESS_KEY="<storage-account-key>"
   ```

3. **आंशिक कॉन्फ़िग के साथ बैकएंड को इनिशियलाइज़** करें:

   ```sh
   cd terraform
   terraform init -backend-config=backend.hcl
   ```

4. **फ़ॉर्मेटिंग जांचें और वैलिडेट करें:**

   ```sh
   terraform fmt -check -recursive
   terraform validate
   ```

5. **प्लान और अप्लाई करें:**

   ```sh
   terraform plan
   terraform apply
   ```

</Steps>

एक सफल अप्लाई ज़ोन बनाता है और Azure कंटेनर में स्टेट लिखता है। यह पुष्टि करने के लिए कि यह रिज़ॉल्व होता है,
[चरण 2 — सत्यापन](/dns/demo/phase-2-validate/) पर जारी रखें।

## निरंतर एकीकरण

`.github/workflows/terraform.yml` वर्कफ़्लो प्रत्येक पुल रिक्वेस्ट पर **plan** और `main` में मर्ज होने पर
**apply** चलाता है। यह रिपॉज़िटरी चर से बैकएंड निर्देशांक और इनपुट, तथा रहस्यों से क्रेडेंशियल पढ़ता है,
प्रत्येक को केवल उस स्टेप में इंजेक्ट करता है जिसे इसकी आवश्यकता है, और साझा स्टेट ब्लॉब पर दो अप्लाई
कभी प्रतिस्पर्धा न करें इसलिए कंकरेंसी ग्रुप पर रन को क्रमबद्ध करता है।

```yaml
name: Terraform

on:
  pull_request:
    branches: [main]
    paths: ['terraform/**', '.github/workflows/terraform.yml']
  push:
    branches: [main]
    paths: ['terraform/**']

permissions:
  contents: read

concurrency:
  group: terraform-state
  cancel-in-progress: false

env:
  TF_IN_AUTOMATION: 'true'

jobs:
  terraform:
    name: ${{ github.event_name == 'push' && 'apply' || 'plan' }}
    runs-on: ubuntu-latest
    defaults:
      run:
        working-directory: terraform
    steps:
      - name: Checkout
        uses: actions/checkout@9c091bb21b7c1c1d1991bb908d89e4e9dddfe3e0 # v7.0.0

      - name: Setup Terraform
        uses: hashicorp/setup-terraform@dfe3c3f87815947d99a8997f908cb6525fc44e9e # v4.0.1

      - name: Init
        env:
          ARM_ACCESS_KEY: ${{ secrets.ARM_ACCESS_KEY }}
          RESOURCE_GROUP: ${{ vars.TFSTATE_RESOURCE_GROUP }}
          STORAGE_ACCOUNT: ${{ vars.TFSTATE_STORAGE_ACCOUNT }}
          CONTAINER: ${{ vars.TFSTATE_CONTAINER }}
          STATE_KEY: ${{ vars.TFSTATE_KEY }}
        run: |
          terraform init -input=false \
            -backend-config="resource_group_name=${RESOURCE_GROUP}" \
            -backend-config="storage_account_name=${STORAGE_ACCOUNT}" \
            -backend-config="container_name=${CONTAINER}" \
            -backend-config="key=${STATE_KEY}"

      - name: Format check
        run: terraform fmt -check -recursive

      - name: Validate
        run: terraform validate -no-color

      - name: Plan
        if: github.event_name == 'pull_request'
        env:
          ARM_ACCESS_KEY: ${{ secrets.ARM_ACCESS_KEY }}
          XCSH_API_URL: ${{ secrets.XCSH_API_URL }}
          XCSH_API_TOKEN: ${{ secrets.XCSH_API_TOKEN }}
          TF_VAR_domain: ${{ vars.DNS_DOMAIN }}
        run: terraform plan -input=false -no-color

      - name: Apply
        if: github.event_name == 'push'
        env:
          ARM_ACCESS_KEY: ${{ secrets.ARM_ACCESS_KEY }}
          XCSH_API_URL: ${{ secrets.XCSH_API_URL }}
          XCSH_API_TOKEN: ${{ secrets.XCSH_API_TOKEN }}
          TF_VAR_domain: ${{ vars.DNS_DOMAIN }}
        run: terraform apply -input=false -auto-approve -no-color
```

एक्शन को कमिट SHA पर पिन किया गया है (संस्करण टिप्पणियों के साथ), और रहस्य पूरे जॉब के बजाय
`init`, `plan`, और `apply` स्टेप तक सीमित हैं।
