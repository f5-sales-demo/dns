第一阶段使用 Terraform 在 F5 Distributed Cloud 上部署一个权威的**主 DNS 区域**，并以 Azure Blob 存储作为远程状态后端。本页展示了计划中的所有文件，说明了所需的变量和密钥，并涵盖了本地运行和 GitHub Actions 流水线两种方式。

## 部署内容

- 一个 `xcsh_dns_zone`，用于您的委托域名，位于 `system` 命名空间中，包含一个 `demo-records` A 记录组（`www`、`app`、`api`）。
- Terraform 状态存储在 Azure Blob 存储容器中，使您的本地计算机与 CI 共享同一状态。

<Aside type="note">
DNS 对象必须在 `system` 命名空间中创建——F5 XC API 会拒绝其他命名空间。区域名称必须是您账户拥有的域名，且记录 TTL 必须至少为 60 秒。
</Aside>

## 计划结构

计划位于 `terraform/` 目录下：一个精简的根模块，将输入传递给 `dns-zone` 模块。

### versions.tf

固定 Terraform 及提供程序的版本。提供程序约束为 `>= 3.61.15`——这是第一个包含 DNS 资源的注册表版本。

```hcl
terraform {
  required_version = ">= 1.5"

  required_providers {
    xcsh = {
      source = "f5-sales-demo/xcsh"
      # >= 3.61.16: the namespace attribute for system-only DNS resources defaults
      # to "system" (spec-driven), so it can be omitted. Locally the provider is
      # consumed via dev_overrides, which ignores this constraint.
      version = ">= 3.61.16"
    }
  }
}
```

### providers.tf

提供程序在代码中不接受任何参数——它通过环境变量进行身份验证，因此不会提交任何密钥。

```hcl
# The xcsh provider authenticates from the environment — no secrets in code.
# Export one of the following credential sets before running Terraform:
#
#   Token auth:  XCSH_API_URL + XCSH_API_TOKEN
#   P12 auth:    XCSH_API_URL + XCSH_P12_FILE + XCSH_P12_PASSWORD
#   PEM auth:    XCSH_API_URL + XCSH_CERT + XCSH_KEY
#
# See terraform/README.md for local dev setup (dev_overrides + env).
provider "xcsh" {}
```

### backend.tf

一个**部分**配置的 `azurerm` 后端：不硬编码任何特定于环境的值。相关配置在 `init` 阶段提供（本地通过文件，CI 中通过 GitHub Actions 变量）。

```hcl
terraform {
  # Azure Blob Storage remote state, configured as a PARTIAL backend:
  # no environment-specific values are hardcoded here. Supply them at init time.
  #
  #   CI:    terraform init -backend-config="resource_group_name=$RG" ...
  #          (values from GitHub Actions repository variables)
  #   Local: terraform init -backend-config=backend.hcl   (copy backend.hcl.example; gitignored)
  #
  # Auth is the storage account access key via the ARM_ACCESS_KEY environment
  # variable (never committed). Keyless auth (use_oidc / use_azuread_auth) is not
  # used: our Contributor-only RBAC cannot assign the "Storage Blob Data
  # Contributor" role those methods require.
  backend "azurerm" {}
}
```

### variables.tf

`domain` 为必填项（在运行时提供，不可硬编码）；`a_records` 将每条记录名映射到其 IPv4 地址。此处没有 `namespace` 变量——提供程序根据 API 规范约束将 DNS 对象固定到 `system` 命名空间，因此无需在此处配置。

```hcl
variable "domain" {
  description = "DNS zone FQDN (required; supplied via TF_VAR_domain / a GitHub variable / tfvars)."
  type        = string
}

variable "labels" {
  description = "Labels applied to managed DNS objects."
  type        = map(string)
  default = {
    managed_by = "terraform"
    use_case   = "dns"
  }
}

variable "a_records" {
  description = "A records: record name (\"\" = apex) to list of IPv4 addresses."
  type        = map(list(string))
  default = {
    www = ["203.0.113.10"]
    app = ["203.0.113.20"]
    api = ["203.0.113.30"]
  }
}
```

<Aside type="tip">
默认 A 记录使用 RFC 5737 文档地址（`203.0.113.0/24`），该地址不可路由。如需用于实际演示，请将其替换为真实目标地址。
</Aside>

### main.tf 与 dns-zone 模块

根模块将输入传递给 `./modules/dns-zone`：

```hcl
module "dns_zone" {
  source = "./modules/dns-zone"

  domain    = var.domain
  labels    = var.labels
  a_records = var.a_records
}
```

该模块负责创建区域（命名空间被省略——提供程序默认将其设为 `system`）。`dynamic "rr_set"` 块将 `a_records` 映射转换为每条记录一个记录集：

```hcl
resource "xcsh_dns_zone" "this" {
  name   = var.domain
  labels = var.labels

  primary {
    default_soa_parameters {}

    rr_set_group {
      metadata {
        name = "demo-records"
      }

      dynamic "rr_set" {
        for_each = var.a_records
        content {
          ttl = var.record_ttl
          a_record {
            name   = rr_set.key
            values = rr_set.value
          }
        }
      }
    }
  }
}
```

根目录的 `outputs.tf` 从模块中重新导出区域名称和 F5 XC 标识符。

## 所需变量和密钥

`.tf` 文件中不包含任何特定于环境的配置。所有内容均在运行时提供——在 CI 中来自 GitHub Actions 的**变量**和**密钥**，在本地来自文件和环境变量。

| 值 | 用途 | CI 来源 | 本地来源 |
| --- | --- | --- | --- |
| `resource_group_name`、`storage_account_name`、`container_name`、`key` | azurerm 后端配置坐标 | 仓库**变量** `TFSTATE_RESOURCE_GROUP`、`TFSTATE_STORAGE_ACCOUNT`、`TFSTATE_CONTAINER`、`TFSTATE_KEY`（通过 `-backend-config` 传入） | `backend.hcl`（从 `backend.hcl.example` 复制；已添加至 .gitignore） |
| `domain` | Terraform 输入变量 | 仓库**变量** `DNS_DOMAIN`（作为 `TF_VAR_domain`） | `terraform.tfvars`（从示例复制）或 `TF_VAR_domain` |
| `ARM_ACCESS_KEY` | azurerm 后端身份验证（存储账户密钥） | 仓库**密钥** | `export ARM_ACCESS_KEY=...` |
| `XCSH_API_URL`、`XCSH_API_TOKEN` | xcsh 提供程序身份验证 | 仓库**密钥** | `export XCSH_API_URL=... XCSH_API_TOKEN=...` |

仓库中附带的两个示例文件：

<Tabs>
<TabItem label="backend.hcl.example">

```hcl
resource_group_name  = "f5-sales-demo-tfstate"
storage_account_name = "f5salesdemotfstate"
container_name       = "tfstate"
key                  = "dns.tfstate"
```

</TabItem>
<TabItem label="terraform.tfvars.example">

```hcl
domain = "f5-sales-demo.com"

labels = {
  managed_by = "terraform"
  use_case   = "dns"
}

a_records = {
  www = ["203.0.113.10"]
  app = ["203.0.113.20"]
  api = ["203.0.113.30"]
}
```

</TabItem>
</Tabs>

<Aside type="caution">
后端身份验证使用存储账户访问密钥（`ARM_ACCESS_KEY`），而非无密钥的 OIDC / Azure AD 方式。无密钥数据平面访问需要 *Storage Blob Data Contributor* 角色，而仅具有 Contributor 权限的订阅无法分配该角色。访问密钥仅存在于环境变量或 GitHub 密钥中——永远不会被提交到代码库。
</Aside>

## 引导 Azure 状态后端

由于后端存储无法保存自身的引导信息，因此需要通过已认证的 Azure CLI 会话在带外操作中一次性创建。仓库附带了 `scripts/bootstrap-azure-state.sh`：

```sh
az group create --name f5-sales-demo-tfstate --location eastus2 \
  --tags managed_by=terraform use_case=dns purpose=tfstate

az storage account create --name f5salesdemotfstate --resource-group f5-sales-demo-tfstate \
  --location eastus2 --sku Standard_LRS --kind StorageV2 \
  --min-tls-version TLS1_2 --allow-blob-public-access false

# State safety: keep prior versions and allow recovery of deleted state blobs.
az storage account blob-service-properties update \
  --account-name f5salesdemotfstate --resource-group f5-sales-demo-tfstate \
  --enable-versioning true \
  --enable-delete-retention true --delete-retention-days 7 \
  --enable-container-delete-retention true --container-delete-retention-days 7

KEY="$(az storage account keys list \
  --account-name f5salesdemotfstate --resource-group f5-sales-demo-tfstate \
  --query '[0].value' -o tsv)"

az storage container create --name tfstate \
  --account-name f5salesdemotfstate --auth-mode key --account-key "$KEY"
```

然后将密钥导出以供本地运行使用，并将其（以及提供程序凭据）设置为 GitHub 密钥：

```sh
export ARM_ACCESS_KEY="$KEY"
gh secret set ARM_ACCESS_KEY -R f5-sales-demo/dns
gh secret set XCSH_API_URL   -R f5-sales-demo/dns
gh secret set XCSH_API_TOKEN -R f5-sales-demo/dns
```

## 本地部署

<Steps>

1. **配置输入。** 复制示例文件并填入您的值：

   ```sh
   cp terraform/backend.hcl.example terraform/backend.hcl
   cp terraform/terraform.tfvars.example terraform/terraform.tfvars
   ```

2. **导出凭据：**

   ```sh
   export XCSH_API_URL="https://<tenant>.console.ves.volterra.io"
   export XCSH_API_TOKEN="<api-token>"
   export ARM_ACCESS_KEY="<storage-account-key>"
   ```

3. 使用部分配置**初始化**后端：

   ```sh
   cd terraform
   terraform init -backend-config=backend.hcl
   ```

4. **检查格式并验证：**

   ```sh
   terraform fmt -check -recursive
   terraform validate
   ```

5. **规划并应用：**

   ```sh
   terraform plan
   terraform apply
   ```

</Steps>

成功应用后，区域将被创建，状态将写入 Azure 容器。继续前往[第二阶段 — 验证](/dns/demo/phase-2-validate/)以确认解析是否正常。

## 持续集成

`.github/workflows/terraform.yml` 工作流在每个 Pull Request 上执行**规划**，并在合并到 `main` 分支时执行**应用**。它从仓库变量中读取后端配置坐标和输入，从密钥中读取凭据，仅将每项内容注入到需要它的步骤中，并通过并发组串行化运行，确保两次应用不会同时竞争共享的状态 blob。

```yaml
name: Terraform

on:
  pull_request:
    branches: [main]
    paths: ['terraform/**', '.github/workflows/terraform.yml']
  push:
    branches: [main]
    paths: ['terraform/**']

permissions:
  contents: read

concurrency:
  group: terraform-state
  cancel-in-progress: false

env:
  TF_IN_AUTOMATION: 'true'

jobs:
  terraform:
    name: ${{ github.event_name == 'push' && 'apply' || 'plan' }}
    runs-on: ubuntu-latest
    defaults:
      run:
        working-directory: terraform
    steps:
      - name: Checkout
        uses: actions/checkout@9c091bb21b7c1c1d1991bb908d89e4e9dddfe3e0 # v7.0.0

      - name: Setup Terraform
        uses: hashicorp/setup-terraform@dfe3c3f87815947d99a8997f908cb6525fc44e9e # v4.0.1

      - name: Init
        env:
          ARM_ACCESS_KEY: ${{ secrets.ARM_ACCESS_KEY }}
          RESOURCE_GROUP: ${{ vars.TFSTATE_RESOURCE_GROUP }}
          STORAGE_ACCOUNT: ${{ vars.TFSTATE_STORAGE_ACCOUNT }}
          CONTAINER: ${{ vars.TFSTATE_CONTAINER }}
          STATE_KEY: ${{ vars.TFSTATE_KEY }}
        run: |
          terraform init -input=false \
            -backend-config="resource_group_name=${RESOURCE_GROUP}" \
            -backend-config="storage_account_name=${STORAGE_ACCOUNT}" \
            -backend-config="container_name=${CONTAINER}" \
            -backend-config="key=${STATE_KEY}"

      - name: Format check
        run: terraform fmt -check -recursive

      - name: Validate
        run: terraform validate -no-color

      - name: Plan
        if: github.event_name == 'pull_request'
        env:
          ARM_ACCESS_KEY: ${{ secrets.ARM_ACCESS_KEY }}
          XCSH_API_URL: ${{ secrets.XCSH_API_URL }}
          XCSH_API_TOKEN: ${{ secrets.XCSH_API_TOKEN }}
          TF_VAR_domain: ${{ vars.DNS_DOMAIN }}
        run: terraform plan -input=false -no-color

      - name: Apply
        if: github.event_name == 'push'
        env:
          ARM_ACCESS_KEY: ${{ secrets.ARM_ACCESS_KEY }}
          XCSH_API_URL: ${{ secrets.XCSH_API_URL }}
          XCSH_API_TOKEN: ${{ secrets.XCSH_API_TOKEN }}
          TF_VAR_domain: ${{ vars.DNS_DOMAIN }}
        run: terraform apply -input=false -auto-approve -no-color
```

Actions 被固定到提交 SHA（附有版本注释），密钥的作用域限定在 `init`、`plan` 和 `apply` 步骤，而非整个作业。
