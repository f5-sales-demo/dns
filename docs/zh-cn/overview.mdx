本用例使用 Terraform 在 **F5 Distributed Cloud 上管理权威 DNS**。一个精简且可复用的计划为委派域创建主要 DNS 区域及其记录，将状态保存在 **Azure Blob Storage** 中，并通过 **GitHub Actions** 实现拉取请求时执行 plan、合并时执行 apply 的自动化流程。

## 管理内容

- 一个 `xcsh_dns_zone`——位于 F5 XC `system` 命名空间中的权威**主要**区域，包含 A 记录。区域名称为委派域（通过变量配置），因此重新定向目标只需修改配置，而无需修改代码。
- 存储于 Azure 的远程 Terraform 状态，使运维人员的本地机器与 CI 之间可共享执行环境。

## 架构

| 层级 | 选择 | 原因 |
| --- | --- | --- |
| Provider | `f5-sales-demo/xcsh`（Terraform 注册表） | 基于 F5 XC OpenAPI 生成；管理 `xcsh_dns_zone` 及 DNS 负载均衡器资源。使用 API 令牌进行身份验证（`Authorization: APIToken <token>`）。 |
| 状态后端 | `azurerm`（Azure Blob Storage），访问密钥认证 | 持久化、可共享的状态存储。使用访问密钥认证，原因在于该订阅仅授予了 Contributor 角色，无法分配无密钥（OIDC / Azure AD）认证所需的 *Storage Blob Data Contributor* 角色。 |
| 自动化 | GitHub Actions | 每次拉取请求时执行 plan，合并到 `main` 时执行 apply。后端协调参数和输入来自仓库**变量**；凭据来自**密钥**。 |

<Aside type="note">
所有 F5 XC DNS 对象必须位于 `system` 命名空间中——API 会拒绝其他命名空间。该计划通过变量验证规则强制执行此约束。
</Aside>
